Xerox PARC, 1979

It began as a calendar.

David Gifford was a graduate student at Stanford University, and the thing he was building was "a distributed calendar system" called Violet. It kept each calendar file on several machines so you could read it with a server down. The published rule was update a majority of the copies. Gifford wanted a fast local copy to outweigh a slow remote one, so he stopped counting copies and gave each votes.

A read gathers r votes. A write gathers w votes. He required "r + w is greater than the total number of votes assigned to the file". Two sets that big cannot avoid each other. That is not a side effect, it is the guarantee: "This ensures that there is a non-null intersection between every read quorum and every write quorum."

It is half a mechanism. Being handed a current copy is not knowing which one it is, so the abstract adds: "Version numbers make it possible to determine which copies are current."

Then the bill, in his own tables. A worst-case first read: 8m-2 messages, four round-trip delays. Tune for cheap reads — r=1, w=3 across three servers — and a write takes 750 milliseconds and fails if one server blinks.

Which weights? The table assumes the probability a representative is unavailable is .01, and leaves the rest to "knowledgeable system administrators".

Gifford could not say how to set r and w. What would you need to know about a piece of data first?
