The interviewer writes a hashtag on the whiteboard and says: "Design trending topics. Every public event on the platform flows to you — every video view, every search, every hashtag use. Show me the top ten right now, for the last hour and the last day, and keep it fresh." Then the number drops: "Ten million events per second."

Your first instinct is everyone's first instinct, and it's the trap the question was built around: dump events into a store and run SELECT key, COUNT(*) GROUP BY key ORDER BY count DESC LIMIT 10. At ten million writes per second, over a sliding window, with a fresh answer due every few seconds — that query isn't slow. It's fictional. No database on earth runs it at this rate on live data.

What makes this a senior favorite is that the honest answer requires giving up something engineers hate giving up: exactness. The passing candidate says, early and out loud, "I cannot count this exactly in real time, and I'm going to prove it with arithmetic — so I'll count it approximately now and exactly later." Everything else in the design falls out of that one committed sentence. This chapter is that interview, played at the E5 bar. It's also the payoff chapter for the probabilistic structures you met in Part 2 — this is the problem count-min sketch was born for.

Requirements: pin the product before the plumbing

First, shrink the problem out loud. "Top-K" and "trending" sound like one feature. They're two, and I'll say so at the whiteboard: top-K is "biggest counts in a window" — most-viewed videos this hour. Trending is "rising fastest against its own baseline" — a hashtag doing 50x its normal rate. Same pipeline, different final scoring. I'll build the counting machine once and hang both scores off it.

Functional requirements:

  • Top-K most-frequent keys (hashtags, video IDs, search queries) over sliding windows: last 5 minutes, last hour, last 24 hours.
  • K is configurable from 10 (a trends widget) up to 1,000 (an internal dashboard).
  • A separate "trending" list ranked by rise-over-baseline, not raw volume.
  • A read API that any surface (home page, search page) can call.
  • Out of scope, agreed with the interviewer: personalization, spam/bot filtering (I'll assume a filter stage upstream owns that), and historical analytics UI.

Non-functional requirements — with numbers I'm committing to:

  • Ingest 10M events/second at peak, with spikes beyond during global moments.
  • Leaderboard freshness: results at most ~5 seconds stale. Near-real-time, not real-time — I'm saying that out loud because it buys me the whole design.
  • Counts may be approximate for display (within roughly 1% on the big entries), but must become exact in the historical record within hours.
  • Read latency p99 under 100ms — which will turn out to be trivial.
  • Availability beats freshness for the widget: serving a 30-second-old list is fine; serving an error is not.

Estimation: the number that forces the whole design

This is the rare problem where estimation isn't a warm-up — it is the argument. I want to prove the naive design impossible, with arithmetic, before I replace it.

Volume. 10M events/sec ≈ 864 billion events/day — call it a trillion. At ~100 bytes per event that's about 1 GB/s of ingest, roughly 86 TB/day of raw log. Big, but a log is the easy part: Kafka and object storage eat this for breakfast.

Distinct keys. Billions of videos exist; hundreds of millions get at least one view a day; add search queries (near-unbounded) and hashtags. Call it ~2 billion distinct keys touched per day.

Now the kill shot: what does exact counting cost? A hash map from key to count: ~8 bytes of hashed key, 8 bytes of count, plus buckets, pointers, and load-factor slack — realistically ~100 bytes per entry. 2 billion keys × 100 bytes = 200 GB of RAM for one window. But a sliding hour needs me to expire per-minute contributions, so I really need counts per key per minute — that multiplies the state again. And whatever holds it must absorb 10M random-access writes per second, and be snapshotted every minute, and be rebuilt when a node dies. This isn't "add more machines" territory; it's a structurally wrong shape. Meanwhile, here's the punchline I want the interviewer to hear: a count-min sketch giving useful accuracy at this traffic costs ~16 MB. Not gigabytes — megabytes — because its size doesn't depend on the number of distinct keys at all.

Three conclusions, each driving a decision:

  • Exact real-time counting of all keys is off the table → the live path uses sketches (approximate, fixed memory).
  • Exactness is still required eventually → keep the raw log and run exact batch counts over it hourly. Two paths, merged.
  • The read side is one small cached blob (K ≤ 1,000 entries ≈ 50 KB) → reads are trivial. All the difficulty lives in the write/aggregation path, so that's where I'll spend the interview.

API and data model — quickly

The public surface is one endpoint:

GET /trending?window=1h&k=50&mode=top|rising
→ { "as_of": 1723620004, "window": "1h", "entries": [
     { "key": "#eclipse", "rank": 1, "count_est": 41200000 }, ... ] }

Note count_est, not count — the field name admits the approximation, and the UI rounds ("41.2M") the way every view counter you've ever seen does. Internally: an event stream {type, key, geo, ts} partitioned by hash(key); in-memory sketch state on counting shards; a Redis leaderboard blob per (window, mode); and a warehouse table exact_counts(key, hour, count) written by the batch path.

High-level design: one machine, two speeds

Write path. Every event lands in Kafka, partitioned by hash(key) — so all events for #eclipse flow to the same partition, and one counting shard owns each key's full stream. Each of ~50 counting shards consumes its partitions and maintains, in memory, a ring of per-minute count-min sketches plus small heaps of candidate top keys (deep dive 1). Every 2 seconds, an aggregator pulls each shard's current candidates with their window counts, merges them, and writes the top-K blob for each window into the leaderboard cache.

Read path. An API server answers GET /trending straight from the cache. One blob, a few kilobytes, refreshed every 2 seconds — even 100K read QPS is a non-event, and a CDN could take it further. I'll say this once and move on: the read path is deliberately boring.

Slow path. Kafka also archives everything to object storage in hourly partitions. An hourly batch job (Flink or Spark — I'll say Flink in batch mode) computes exact counts per key per hour: a shuffle-and-sum over ~36 billion events, a thoroughly ordinary big-data job. It writes exact hourly top-K into the historical store, overwriting the approximate snapshots the fast path recorded, and feeds the diff alarm that compares the two paths (failure section).

Why two paths — isn't this the "lambda architecture" everyone spent the 2010s arguing about? Yes, and I'm choosing it on purpose, so let me defend it. The pure-streaming alternative (kappa: one exactly-once stream job holding exact keyed counts) re-imports the very problem my estimation ruled out: exact per-key state for billions of keys, now spread across a giant stateful cluster with checkpoint and recovery pain to match. Here the product genuinely tolerates approximation for the live number and genuinely wants exactness only for the record — that split in requirements is exactly when lambda earns its keep. The cost is real and I'll name it before the interviewer does: two codepaths that can disagree, and I must monitor their disagreement rather than assume it away. That monitor turns out to be a feature — it's my correctness alarm.

War story — Twitter, Storm, and where "lambda" came from

This exact design has a birthplace. In 2011 Twitter acquired BackType, a social-analytics startup whose engineer Nathan Marz had built Storm — the first widely used open-source stream processor, released that September. Storm became Twitter's real-time analytics backbone, and the canonical demo topology was literally this chapter: a rolling, sharded count of the top-N words and hashtags in the firehose. Marz then wrote up the pattern he'd been living: you can't afford exact real-time computation over the full history, so you run a fast approximate "speed layer" beside a slow exact "batch layer" and merge them at query time — he named it the Lambda Architecture, and argued the batch layer also buys "human fault tolerance": when a bug corrupts your live numbers, recomputing from the immutable log fixes history. The pattern drew famous criticism (Jay Kreps' "kappa" essay: two codepaths, double maintenance), and for many pipelines kappa won. But top-K at firehose scale is the workload lambda was invented for — and Twitter kept investing in the fast layer for years, replacing Storm in 2015 with Heron, an API-compatible engine it built for better debuggability and efficiency, described in a published SIGMOD paper.

Deep dive 1: the fast path — a sketch and a heap

The crux

The hard part of this whole problem is one sentence: you cannot afford a counter per key, and you cannot rank what you never stored. Everything hinges on two structures working as a pair. The count-min sketch answers "roughly how many times have I seen this key?" in fixed memory — but it cannot list keys; it only answers questions about keys you name. The min-heap remembers which keys are currently worth naming. Sketch = counts without names; heap = names without counts. Candidates who reach for just one of the two get stuck in front of the interviewer: a sketch alone can't produce a top-10 list, and a heap alone has no counts to rank by. The pair — plus the fact that sketches merge cleanly — is the entire trick, and it's where this interview is won.

A count-min sketch (Part 2, chapter 10 — here's the payoff) is a small 2-D array of counters: d rows, w columns. Each row has its own hash function. The mechanics, walked honestly:

  • Update: for an event on key x, compute d hashes; in each row i, increment cell [i][h_i(x)]. That's it — four hashes, four increments. Nanoseconds.
  • Query: read those same d cells and take the minimum. Other keys hash-colliding into a cell can only have added to it, so every cell is an overcount; the minimum is the least-polluted view.
  • Error direction: therefore the estimate is never below the true count, and above it by at most about (e/w) × N with high probability, where N is the total number of events the sketch has absorbed. Deeper (d) makes a bad overestimate exponentially less likely; wider (w) shrinks the overestimate itself.
Analogy

A count-min sketch is a wall of shared tally counters. You don't get your own counter — you get assigned one by hash, and strangers share it with you, clicking it up for their own keys. So any single counter reads too high, never too low. The fix: assign everyone four counters on four differently-shuffled walls, and when asked for your count, report the smallest of your four — it's the one the fewest strangers polluted. The analogy breaks in one place worth saying: real tally walls run out of counters; a sketch never refuses a new key. It just gets statistically noisier as N grows — which is exactly the knob we'll tune.

Sizing — one worked example, because the interviewer will ask. I'll commit: w = 1M cells, d = 4, 4-byte counters → 16 MB per sketch. Error ≈ e/w ≈ 2.7 per million events absorbed. For a full merged hour of global traffic (N ≈ 36 billion), that's an overcount of roughly 100K on any query, wrong by more only ~2% of the time (that's the d = 4 doing its job). A top hashtag in that hour sits around 36M+ events, so we're ranking with ~0.3% noise. For the entries that matter, that's invisible. Note the trade honestly: error scales with total traffic through the sketch, not with distinct keys — the knob is width, and I'll come back to it in ops.

Now the heap. The sketch can't tell me which keys are big — I can only ask it about keys I name. So each shard keeps a min-heap of the current candidates: on each event, query the sketch for that key's estimate; if the key is already in the heap, update it; otherwise, if the estimate beats the heap's smallest member, evict the smallest and admit the newcomer. A hash-set alongside gives O(1) membership checks. I'll keep per-minute heaps of ~2,000 candidates per shard — far more than K, deliberately, so real risers can't slip through the cracks between minutes.

What the overestimate does to top-K — and who's allowed to care. Since estimates only err upward, the failure mode is a false entrant: a middling key whose four cells all got unlucky collisions sneaks in near the boundary — rank 9 or 10 in a top-10, the tail of a top-1000. It can bump a legitimate key out. Ranks 1 through 5, separated by millions, are effectively immune; the noise lives where neighbors are ~100K apart. My commitment: for a trends widget or a "popular now" shelf, boundary churn is invisible and acceptable. For anything with money or contracts attached — advertiser reporting, creator payouts — it is not, and those numbers must come from the exact path, full stop. There's even a useful asymmetry to name: threshold alerts built on CMS can fire falsely but can never miss a genuinely hot key, because estimates never read low.

War story — Reddit counts views with a sketch's cousin

In 2017 Reddit's engineering blog laid out how they built per-post view counts — the little "N views" number — and it's a confession that exact counting loses at scale. They wanted unique viewers per post, and for a viral post that means tracking millions of distinct user IDs; keeping a real set per post would burn megabytes each across millions of posts, almost all of it for a number nobody audits. Their pipeline: every view event flows through Kafka into a consumer named Nazar that filters and dedups (deciding whether a view is countable at all), then into a counter service named Abacus that maintains the count in Redis using HyperLogLog — a probabilistic structure that estimates distinct-count in about 12 KB regardless of whether a post had ten thousand or ten million viewers. They accepted roughly 1% error, permanently, in a user-facing number, and traded it for fixed tiny memory. Different sketch than ours — HLL answers "how many distinct?", CMS answers "how many times?" — but the identical senior judgment: measure what exactness costs, notice nobody needs it here, and say so in the design doc.

Deep dive 2: windows that slide, and what "trending" actually ranks

"Last hour" is a sliding window: at 12:47 it means 11:47→12:47. Rebuilding a sketch of 36 billion events every 2 seconds is obviously out, so I'll do what nearly every production system does: quantize. Each shard keeps one sketch per minute — a tumbling window that closes and becomes immutable when the minute rolls over — arranged in a ring of 60. The current minute's sketch is the only one being written. A query for the sliding hour reads all 60: because sketches with the same dimensions and hash seeds merge by element-wise addition of their counter arrays, summing a key's estimate across the ring gives its count for the trailing hour. When minute 61 begins, the ring's write head advances and the oldest sketch is wiped and reused — expiry is free, no tombstones, no compaction.

Analogy

It's a clock face of 60 small notebooks. You only ever write in the notebook for the current minute. Anyone asking "what happened in the last hour?" reads all 60 and adds them up. When a new minute starts, you grab the oldest notebook, erase it, and start writing — no shredding ceremony, no archive room. The honest cost: your "hour" is really "the last 59-to-60 whole minutes," quantized to minute edges. Nobody staring at a trends widget can tell, and I'll say so rather than hide it.

The day window works the same way one level up: when a minute-ring bucket retires, its contents have already been folded (added, cell by cell) into the current hour sketch, and 24 hourly sketches in a second ring give me the sliding day. Memory per shard: 60 × 16 MB + 24 × 16 MB + heaps ≈ 1.4 GB. Comfortable on one box, with room for 10x.

One subtlety I'd volunteer before the interviewer finds it: how do shards afford window queries for thousands of candidates? Answer: incrementally. When a key first enters a candidate heap, the shard sums its ring once and caches that windowed count; afterwards it just adds live increments as they happen and, at each minute rollover, subtracts the expiring bucket's contribution for each cached candidate. A few thousand candidates × 60-bucket touch-ups per minute is noise.

Now "trending," which is a different question than "big." A top-K-by-volume list is Sisyphus content: the same megastars every day. Trending must rank acceleration: current rate against the key's own baseline. My committed score: score = (c_now + s) / (c_base + s), where c_now is the key's last-15-minutes count, c_base is its average 15-minute count over the trailing day (both straight from the rings), and s is a smoothing constant (say 5,000) that stops a key going 3 → 300 views from "trending" at 100x. Plus a floor: ignore keys below a minimum current volume. Rank candidates by score instead of count, and the same machine serves both lists. This velocity-over-volume choice is not academic — Twitter said publicly, back in 2010, that trends are computed to surface sharp spikes over sustained volume, which is precisely why Justin Bieber famously stopped being a permanent fixture of the trends box despite having more raw tweet volume than almost anything else on the platform. Volume is fame; trending is news.

Deep dive 3: sharding, merging, and the viral-key question

I partitioned by hash(key), so here's the question I should raise before the interviewer does: a viral key is one key. When #eclipse does 3M events/sec, every one of them lands on the same partition, the same shard. Did I just build chapter p2c06's hot-partition nightmare on purpose?

No — and the reason is worth spelling out, because it's the difference between this system and a normal database. A hot key in Postgres means row locks, index contention, disk. A hot key here means four hashes and four integer increments, no locks, no allocation, memory that's already resident. One core sustains millions of these per second; a shard has many cores. And the stream layer helps before events even arrive: producers pre-aggregate — instead of shipping 3M individual {#eclipse, +1} events, each producer batches a few hundred milliseconds locally and ships {#eclipse, +2,913} deltas. A viral key collapses under pre-aggregation (millions of events, one key), so the hotter the key, the better batching works. Sketches absorb the celebrity problem; that's half the reason I chose them.

Key-hash partitioning also buys correctness cheaply: each key's counts live wholly on one shard, so a shard's estimate for its keys is the global estimate — no cross-shard reconciliation per key. The aggregator's merge every 2 seconds is then almost embarrassingly simple: each shard sends its top ~2,000 candidates per window with their ring-summed counts (~50 shards × 2K entries × 40 bytes ≈ 4 MB per pull); the aggregator unions them, sorts, takes K, writes the cache blob.

That inset deserves one careful paragraph, because interviewers probe it and candidates fumble it. Count-min sketches over two disjoint streams merge by adding corresponding cells — every cell is a sum of contributions, so the union's cells are the sums of the parts, and all error guarantees carry over. People say "max" here surprisingly often, because HyperLogLog — the other famous sketch — does merge by taking the max of corresponding registers (its registers record maxima of hash patterns, not sums). Mixing up the two isn't trivia: merge CMS with max and every key that spans sketches gets silently undercounted. Mergeability is also why this architecture recovers well: any set of per-shard, per-minute sketches can be recombined later, in any grouping — across time (the ring sum), across shards (if I ever switch to random partitioning), or across datacenters.

So where's the real pinch point? The aggregator. It's a fan-in of one: every shard reports to it, its cadence sets the freshness SLO, and at 10x shards its pull-merge-sort loop and connection fan-in grow linearly. My answer, committed: it's nearly stateless (its whole world is rebuilt from shard pulls every 2 seconds), so I run two of them in an active-passive pair with a fencing token on cache writes (chapter p2c03) — a stale ex-leader must not overwrite fresher blobs. At 10x I make it a two-level merge tree: 10 mid-level mergers each own 50 shards, one root merges 10 pre-sorted lists. Merge trees are how this design scales sideways forever.

Failure modes and operations — before you ask

Counting shard dies. The state at risk is its rings. Closed minute-sketches are immutable, so each is checkpointed to object storage on rollover — 16 MB a minute, trivial. Recovery: a replacement downloads the 59 closed minutes and replays only the current minute from Kafka (consumer offsets mark the spot) — that's ~12M events, tens of seconds. Until it's back, the leaderboard is missing one shard's candidates; I'd rather serve a list that's briefly blind to 2% of keys than serve nothing, and the diff alarm will tell me if that blindness ever mattered.

Aggregator dies. Nearly nothing is lost — its state regenerates from the next round of shard pulls. The standby fences, takes over, and the cache goes at most a few refresh cycles stale. This "stateless-ish recovery" is a direct dividend of pushing all real state down into mergeable sketches.

The fast and slow paths disagree. This is the alarm I care about most, because it's the only end-to-end correctness check an approximate system has. Every hour, when exact batch counts land, a comparator scores the fast path's archived snapshots against truth: top-10 overlap (should be 10/10, alert under 8), and relative count error on the head (alert above ~2%). Divergence means something structural — a shard silently down, a Kafka partition unassigned, sketch saturation, or mismatched hash seeds after a bad deploy. It's my smoke detector, and it's the second half of why the batch path exists.

Sketch accuracy drifts. Error is ~(e/w) × N: it grows with traffic, not with keys. So the monitor is simple — track N per sketch and the implied error bound versus the count gap around rank K; when the ratio degrades (traffic doubles, say), widen w on the next deploy. Doubling width halves error for double the memory: 32 MB a minute is still nothing. This is a knob you turn twice a year, not a crisis.

Rollout. New scoring formula or resized sketches ship in shadow mode: the new pipeline runs beside the old on the same Kafka stream, publishing to a dark cache, while the comparator scores both against batch truth for a week. Trending is a feedback loop — what you show people changes what they click — so I want numbers before users see anything. Rollback is flipping the serving pointer back.

At 10x (100M events/sec): in order — the aggregator fan-in goes first (fixed: merge tree, above); sketch error bounds go second (fixed: wider sketches, linear memory); Kafka partition count and producer pre-aggregation get retuned; the batch job just runs on more cores. Notably absent from this list: total sketch memory per shard as a function of distinct keys — that's the number that never moves, and it's why this design 10x's gracefully while the hash-map design died in the estimation section.

War story — YouTube's 301 views

For years, every fast-rising YouTube video displayed the same eerie view count: frozen at "301+" while likes and comments kept climbing into the thousands. The mechanism, which YouTube engineers explained publicly after a famous 2012 explainer video made it a meme: below 300 views, the count was cheap and served straight from the fast path — nobody commits fraud for 40 views. Above that threshold, views started to matter (monetization, charts), so the count froze while a slower verification pipeline deduplicated and audited events before updating the public number; the extra "1" was just increments racing the freeze check. YouTube reworked it in 2015 so counts keep updating, but the architecture confession stands, and it's this chapter's design wearing a trench coat: a cheap approximate path for display, an exact audited path for anything with money attached, and a visible seam between them. When your interviewer asks "is approximate really acceptable for users?", this is your answer: the biggest video site on earth froze its most famous number at 301 for years, and the platform thrived.

At the whiteboard — what the interviewer probes next

Once the dual-path design is up, senior-level probing goes straight at the seams:

  • "Your sketch overestimates. Show me a user or a team that overestimation actually hurts." — They want the false-entrant-at-the-boundary story, and the billing/payout line you refuse to cross with approximate numbers.
  • "One hashtag is doing 3M events/sec. Walk me through exactly where that load lands." — They're checking you know a hot key here is increments, not locks — and that pre-aggregation collapses it further.
  • "A counting shard just died. What's lost, and what does recovery look like, minute by minute?" — Checkpointed immutable minutes + replay-the-current-minute is the answer; hand-waving "it's replicated" is not.
  • "Why carry two codepaths? Kreps would say kappa." — Defend lambda for this workload with the state-size math, and concede the maintenance cost honestly.
  • "How would you find out your leaderboard has been quietly wrong for a week?" — If you didn't build the fast-vs-batch diff alarm, this question ends the round.

Compare with a model answer

A hash map needs an entry per distinct key, and we see about two billion keys a day — that's hundreds of gigabytes of RAM being hammered by ten million writes a second, per window, and it dies. A count-min sketch fixes the memory problem by letting keys share a small grid of counters: updating is a few hashes and increments, and its size never grows no matter how many keys exist. The catch is collisions only ever add, so its answers are slightly too high, never too low — and it can't list keys at all, it can only answer "how big is this key?" for keys you name. That's the heap's job: it remembers the current best candidates, admitting a key whenever its sketch estimate beats the smallest member. Together: the sketch holds the counts without the names, the heap holds the names worth ranking. And because it's all approximate, we run an exact batch count over the raw log every hour to correct the record and to alarm if the fast path ever drifts.

Exercises

Product asks for per-country trending — 200 countries, same windows. Naively that's 200 sketch-rings per shard (200 × 16 MB × 60 ≈ 192 GB per shard). Fix the memory without giving up the feature.

Answer

Use the error formula instead of copying the global sizing. CMS error is ~(e/w) × N where N is traffic through that sketch — and a per-country sketch only absorbs that country's events. A country with 1% of traffic needs roughly 1% of the width for the same relative error. So size sketches by country volume: the top handful keep w = 1M, mid-tier countries get 128K, the long tail gets 16K — total lands around 10–15 GB per shard, not 192. Alternatively re-partition by (country, key) so each shard only hosts a few countries' rings. The senior signal is noticing that sketch error scales with traffic, not keys, and letting that asymmetry pay for the feature.

10x the firehose: 100M events/sec. Name what breaks, in order, and the fix for each. Then name the one thing that conspicuously does not break.

Answer

(1) The aggregator's fan-in and merge loop — fix with a two-level merge tree (mid-level mergers own ~50 shards each, root merges pre-sorted lists). (2) Sketch error bounds — error ~(e/w) × N grows 10x with N, so widen w 10x: 160 MB per minute-sketch, ~10 GB per shard ring, still fine on one box. (3) Kafka partition count and producer pre-aggregation windows need retuning; more counting shards come along for the ride. (4) The batch job needs 10x cores — an accounting problem, not a design problem. What doesn't break: per-shard memory as a function of distinct keys — sketches are size-fixed in the dimension that killed the hash map, which is exactly why this design was chosen.

Requirement flip: the consumer of top-K is now the ads team, and the counts feed advertiser billing — exact, auditable, and fresh within ~10 seconds. What survives of your design, and what must change?

Answer

Don't try to tune a sketch into exactness — re-run the estimation, because the requirement flip also flips the key space. Billing counts are per ad campaign, and there are maybe 10 million active campaigns, not 2 billion organic keys. Exact keyed counts for 10M keys ≈ 10M × ~50 bytes ≈ 500 MB — that fits in an exactly-once streaming job's keyed state (Flink with checkpoints, or sharded Redis with an idempotent ledger, chapter p2c02). So the sketch path survives for organic trending, and billing gets its own exact pipeline; the raw-log archive and the diff-alarm habit carry over. The senior move is recognizing that "exact" became affordable the moment the key count shrank — the arithmetic, not the architecture, makes the call.

Sizing drill: one shard's minute-sketch absorbs 12M events. You want overcounts under 1,000 with at least 95% confidence per query. Choose w, d, and compute the memory.

Answer

Target relative error ε = 1,000 / 12M ≈ 8.3 × 10⁻⁵. Width w ≈ e/ε ≈ 2.718 / 0.000083 ≈ 33K cells — round up to 64K for headroom (halves the error, costs nothing). Confidence: failure probability per query ≈ e⁻ᵈ, so d = 3 gives ~5% (borderline) and d = 4 gives ~1.8% — take d = 4. Memory: 64K × 4 rows × 4-byte counters = 1 MB per minute-sketch, 60 MB for the hour ring. The lesson: at per-shard, per-minute granularity, sketches are so cheap that you should always buy an extra factor of 2 on width rather than shave megabytes.

Takeaways
  • The crux is memory arithmetic: billions of distinct keys make an exact real-time hash map cost hundreds of gigabytes, while a count-min sketch costs megabytes because its size is independent of key count.
  • The fast path is a pair with split jobs: the sketch stores counts without names (overestimate-only, tunable via width and depth), and a size-K min-heap stores the names worth ranking.
  • Overestimation's damage is concentrated at the leaderboard boundary — false entrants near rank K — which is acceptable for display surfaces and never acceptable for money.
  • Sliding windows come from tumbling minute buckets in a ring: write one, sum sixty, overwrite the oldest — expiry is free.
  • Count-min sketches merge by element-wise addition of cells (HyperLogLog is the one that merges by max), and that mergeability is what makes sharding, window composition, and recovery cheap.
  • "Trending" ranks velocity against a key's own baseline, with smoothing and a volume floor — a deliberately different metric from top-K by volume, or the list is just celebrities forever.
  • A viral key concentrates on one shard by design and is absorbed there, because sketch updates are lock-free increments and producers pre-aggregate; the true pinch point is the aggregator, fixed with a merge tree and a fenced standby.
  • The exact batch path isn't redundancy — it corrects the historical record and powers the fast-vs-exact diff alarm, the only end-to-end correctness check an approximate system has.
