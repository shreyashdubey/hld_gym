Windows Azure Storage, 2012

An exabyte of data, and one number that picked the code

Cheng Huang's team had the cheap answer already. Azure held three full copies of everything not yet coded; Reed-Solomon (12, 4) would take that to 1.33x — "over 50%" off the cost of storage, and half the data center footprint, as Azure was about to "surpass an Exabyte of storage".

They rejected it — not on cost, on repair: "to do the reconstruction we would need to read from a set of 12 fragments." One offline fragment, twelve reads across the fabric — and at fleet scale, something always is.

So they built Local Reconstruction Codes. Split twelve data fragments into two groups of six, one local parity per group, two global parities across all twelve. Sixteen fragments, still 1.33x — but a lost data fragment rebuilds from six reads, not twelve. In production, a 4 MB reconstruction fell from 893 ms to 418 ms.

The bill is in the fine print. LRC is not maximum-distance-separable. Reed-Solomon survives any four losses; LRC any three, plus only the four-loss patterns that are information-theoretically decodable. They picked which failures to lose.

The write path never got the discount. New data still lands as three copies in an open extent; only when it is sealed and immutable can the coder touch it. You cannot erasure-code bytes that are still arriving.

You run an exabyte at 3x. Attack the overhead or the repair reads? Write it before you read on.
