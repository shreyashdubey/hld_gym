Taobao, 2010

A wish-list page, and a table nobody could cut.

Taobao's Favourites stored what shoppers had saved. Two reads mattered equally: everything one user saved, and everyone who saved one item. Shard on the user and the first hits a single machine; the second has to read every partition. Shard on the item and you only swap which read suffers. One table gets one key.

Alibaba's answer was to write a database. Work began in May 2010. A Taobao engineer posting as Chuanhui published the site's projection in April 2011: a hundred terabytes and a hundred billion records within five years, with hand-cut shards already straining the business.

So they stopped sharding the writes. Yesterday's rows — the baseline — spread across ChunkServers. Everything changed since sat in memory on one UpdateServer, and every read merged the two. One node seeing every write meant cross-row and cross-table transactions needed no distributed coordination.

It shipped. OceanBase has served Taobao Favourites since June 2011 and reached Alipay in 2014. In 2020 it posted 707,351,007 tpmC at CNY 3.98 per tpmC.

The escape hatch was the ceiling. Their own 2023 paper calls that UpdateServer "a single-point write, multi-point read architecture" that "makes it difficult to expand when higher levels of concurrency become necessary." They had escaped distributed transactions by keeping one machine nobody could split.

Two equally important reads, one shard key. Which query do you make expensive, and what do you build to survive it? Write it before you read on.
